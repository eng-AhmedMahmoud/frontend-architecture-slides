Frontend
Architecture

Scaling one real app — CommerceOS — from a monolith to micro-frontends, and how to choose.

Open

We architect frontend today, not just write it. One app, scaled from a simple monolith all the way to micro-frontends, deciding at every step whether the added power is worth the added complexity. The common thread: we trade complexity for scalability.

The big idea

Trade complexity for scalability.

No architecture is "best." Pick the least-worst fit — and move up only when growing pains force it.

The one sentence

Every step up in scalability costs complexity. Our job is to find the best architecture for the scenario, and when we can't, the least-worst one.

01 · Foundations

What is architecture?

"The decisions about how we organize a system to promote the qualities we want" — the ones expensive to change later.

Define it

Ralph Johnson: "the decisions you wish you could get right early." Michael Keeling (Design It): "the decisions about how we organize a system to promote desired quality attributes." Drivers: business goals, quality attributes, constraints, significant requirements, team experience, tech trends → requirements (ADRs) → decisions.

03 · Stage 1 · Monoliths

Growing Pains

  • Lack of organizationharder to find things & onboard people / agents
  • Unclear boundariesno ownership — teams start to step on each other
  • Change amplificationa small change touches files across the codebase
  • Overloaded shared abstractionsthe "common" folder becomes a dumping ground
  • All-or-nothing dependencies · busy CIupgrades are painful; release trains; builds & tests take forever
Growing pains

These are the specific pains that push a monolith toward structure — and eventually toward a monorepo or micro-frontends.

03 · Stage 1 · Failure mode

The "big ball of mud"

A shared table used by orders and customers — a tweak for one breaks the other. Tests miss it.

Name the enemy

A shared order-line-items table with a tooltip-on-timeout is used by both orders and customers; the timeout means tests don't catch it. Implicit cross-module dependency, everywhere.

03 · Stage 1 · The trap 🔑

Modularity before distribution

Add deploy units to a mess → a distributed monolith. Raise modularity first, then distribute.

The senior insight

Two dimensions: deployment units × modularity. Add units without raising modularity first → a distributed big ball of mud. Green arrow up (modularity first), then coral arrow right (distribute). Hover a quadrant to focus it.

03 · Stage 1 · The fix

Modules = business subdomains

Split by domain (DDD), not by tech folder. Read the nav & routes.

Coreorders · catalog
Supportinginventory · customers · analytics
Genericauth · roles · permissions

Structure: modules → screens → features → components. Stay consistent.

DDD subdomains

Core (differentiators), supporting, generic. Find them by reading the nav and routes. Core subdomains get more tests, stronger boundaries, later their own team. Consistency beats the perfect structure.

03 · Stage 1 · Patterns

A menu of patterns

Patterns

Layered, Clean, Hexagonal (ports & adapters), DDD, Atomic, Feature-Slice (great for front end). Don't follow a backend pattern to a T. Formal discovery: the "DDD Starter Modeling Process" repo.

03 · Stage 1 · Two halves

Organization + encapsulation

Organizing folders is only half. Encapsulation — a boundary nothing may cross — is the other half.

  // organization — folders by subdomain
  src/modules/{ catalog, orders, customers, authentication }
  src/shared/            ui · api client · utils

  // encapsulation — deps point DOWN; features never import siblings
The missing half

Encapsulation is familiar from OOP private members, closures, ES-module exports. Architecture has none built in — we create the boundaries. Types: module, layer, information-hiding via interface. Other langs: ArchUnit; JS: ESLint rules.

03 · Stage 1 · Make it stick

A bad import fails CI

Enforced 3 ways: eslint-plugin-boundaries · Dependency Cruiser · Turborepo tags.

Boundaries as code

default:disallow. A module may import platform + itself, never a sibling; allow type-only imports. Errors 106 → 31 → 18 → 2. Dependency Cruiser draws the graph + cohesion checks. These rules are the guardrails AI agents hit on the next lint.

04 · Stage 2

Split into packages

apps/ + packages/ · 3 steps: workspace → packages → tooling · a package's exports = its interface.

Folders become packages

Three-step adoption. App shell (one deploy) + one app per module + packages ui, shared, tooling. Workspaces share without publishing to npm. exports = interface. Still one build.

04 · Stage 2 · Sharing code

Four ways to share

Shared packagesimple · can become a junk drawer
Interfaceexpose only what's needed
Duplicatefine for small logic
Dependency injectionslot pattern — decouples

If everything keeps moving to shared, rethink your abstractions.

Trade-offs

Shared package (junk drawer), interface (exports), duplicate, or dependency injection / slot pattern. If everything migrates to shared, the abstractions are wrong.

04 · Stage 2 · Tooling

Turborepo

Caching + task orchestration + boundary tags · graph + devtools · catches cycles.

Speed + rules

Caching (local+remote) + orchestration. turbo.json: dependsOn ^build, outputs dist; dev persistent. `turbo boundaries` checks cycles, leaks, undeclared deps; tags deny platform → module.

05 · Stage 3

When micro-frontends?

An organizational problem — teams that must deploy independently.

Earn stage 3

Independent deploys, legacy updated piecemeal, diverging drivers. Adopt when coordination cost of the monolith exceeds the distributed-system cost. The dot is the crossover.

05 · Stage 3 · Options

Flavors — start simple

iframeshard isolation · postMessage
Web Componentsruntime + isolation
Module Federationruntime code-sharing · default

Split vertical (by route) or horizontal (part of a view). Cheat: vertical-only → DIY proxy · isolation → iframes · Next.js → multi-zones · else → Module Federation.

The menu

Decide the split (vertical/horizontal), routing/rendering/composition, isolation. Flavors: iframes, web components, native (import maps/ESI), fragment libs (single-spa — unmaintained; Qwik), route-based (Cloudflare, Next multi-zones), Module Federation. Build raw first (DIY: ports + proxy + iframe, same-origin state).

05 · Stage 3

Module Federation

const A = lazy(() => import("analytics/Dashboard"));  // React = singleton
Core mechanism

A host loads remotes at runtime via a generated remoteEntry.js. `shared` negotiates deps — React must be a singleton or context breaks. lazy + Suspense + error boundary; the classic bug is forgetting to await. Host and remotes can be different frameworks → incremental migration.

05 · Stage 3

Keep them independent

Component= reuse
Micro-frontend= independence

Few props · share state via Nanostores — expose a listener, not the atom.

MF 2.0: auto types + mf-manifest.json = service discovery.

Independence is the point

Comms: postMessage / props / events / signals. A component is about reuse, a micro-frontend about independence. Nanostores: the remote owns the atom, exposes a listener. MF 2.0 auto-types + mf-manifest.json = service discovery (AWS, Vercel schemas too).

06 · The payoff

Match the pattern to the pain

Pick by pain, not trend. Modularity before distribution.

The takeaway

The whole course in one table. Always raise modularity before distributing. Smallest architecture that removes the pain wins.
