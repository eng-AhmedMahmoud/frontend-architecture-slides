Senior Frontend Engineering

Frontend Architecture

Scaling one real app — CommerceOS — three ways, and how to choose.

Open

We architect frontend today, not just write it. We take one real app — a Shopify-style admin, CommerceOS — and scale it from a simple monolith all the way to micro-frontends, deciding at every step whether the added power is worth the added complexity. The common thread of the whole talk: we trade complexity for scalability.

The big idea

Trade complexity for scalability.

No architecture is "best." Pick the least-worst fit — and move up only when growing pains force it.

The one sentence

If you remember one thing: every step up in scalability costs complexity. None of these architectures is better than another — each solves a specific problem and has strengths and weaknesses. Our job as architects is to find the best architecture for the scenario, and when we can't, the least-worst one.

01 · Foundations

Architecture = decisions

"The decisions about how we organize a system to promote the qualities we want" — the ones expensive to change later.

Business goals
Quality attributes
Constraintsteam · time · money
→ decisions

These are your architectural drivers. The biggest is usually team size.

Define it

Architecture is hard to define — integration, boundaries, extensibility, scalability all come to mind. The word Maxi uses is "decisions." Ralph Johnson: "the decisions you wish you could get right early." Michael Keeling (Design It): "the decisions about how we organize a software project to promote desired quality attributes." Those decisions come from architectural drivers: business goals, quality attributes, constraints (decisions already made for you — e.g. must deploy to AWS, or time/money), architecturally-significant requirements, team experience, and technology trends (AI). Drivers → requirements (ADRs) → decisions.

01 · Foundations

Compare any architecture

Four pillars — like a character sheet in an RPG.

Style · the "-ilities" · the rules you commit to · the building blocks.

The rubric

From "Fundamentals of Software Architecture." Four pillars: architectural STYLE (the shape — monolith, monorepo, micro-frontends), CHARACTERISTICS (the quality attributes you prioritize), DECISIONS (rules, boundaries), and logical COMPONENTS (modules, screens, features). Maxi's RPG mapping: class = style, stats = characteristics, background = decisions, skills = components. Style alone names the architecture but doesn't paint the full picture — that's why all four matter. We'll give each stage a character sheet.

02 · The map

1 deveverything is fine
5 devsmerge & deploy friction
50 devsone broken build blocks everyone

Move up only when the pain forces it. Complexity you don't need is a bug.

Roadmap

Every architecture pattern exists to answer a growth pain. The axis is team + codebase size. Monolith → Monorepo → Micro-frontends. Note a monorepo isn't technically a style by itself — you can do a monolith or micro-frontends with a monorepo; it just helps with the growing pains.

03 · Stage 1

Start with a monolith

✓ simple · fast to ship
✗ weak stat: scalability

The right default for most teams. The problem is never "monolith" — it's an unstructured one.

Don't dunk on it

Character sheet for the monolithic SPA: promotes simplicity, ease of deployability, easy to maintain. Performance: not the best (client-side SPA), not the worst. The big drawback is scalability. Growing pains: lack of organization, hard to find/maintain, no clear boundaries.

03 · Stage 1 · Failure mode

The "big ball of mud"

A shared table used by orders and customers — a tweak for one breaks the other. Tests miss it.

Name the enemy

Concrete demo: you add a "back to orders" link with a query param (TanStack Router). Ship it. 20 minutes later the customers app breaks — a shared order-line-items table with a tooltip-on-timeout is used by both, and the timeout means tests don't catch it. That implicit cross-module dependency, repeated everywhere, is the big ball of mud.

03 · Stage 1 · The trap 🔑

Modularity before distribution

Add deploy units to a mess → a distributed monolith. Raise modularity first, then distribute.

The senior insight

When the monolith hurts, everyone shouts "micro-frontends!" That's a trap. Two independent dimensions: number of deployment units, and degree of modularity. Big ball of mud = 1 unit, low modularity. Micro-frontends = many units, high modularity. If you add deployment units WITHOUT first raising modularity, you get a distributed big ball of mud — all the old pain plus network, versioning and communication pain. Invest in modularity first (green arrow up), then distribute (blue arrow right).

03 · Stage 1 · The fix

Modules = business subdomains

Split by domain (DDD), not by tech folder. Read the nav & routes.

Coreorders · catalog
Supportinginventory · customers · analytics
Genericauth · roles · permissions

Structure: modules → screens → features → components. Stay consistent.

DDD subdomains

To build a modular monolith, use Domain-Driven Design subdomains to identify modules. Three types: core (make you unique — order management, product catalog), supporting (important but not differentiating — inventory, customers, analytics), generic (every app has them — auth, user management, roles, permissions). Find them by reading the UI: nav and routes. Core subdomains deserve more tests, stronger boundaries, and are the ones most likely to get their own team later. Folder structure: one module per subdomain → screens → features → components (+ api, hooks). Consistency matters more than the exact shape. (Branch: modular-monolith.)

03 · Stage 1 · Patterns

A menu of patterns

LayeredCleanHexagonal (ports & adapters) Domain-Driven DesignAtomic designFeature-Slice design

Most were designed for the back end. Don't force one to the letter — DDD subdomains + feature-slice fit the front end best.

Patterns

Layered (split into layers), Clean (entities/use-cases), Hexagonal (ports & adapters — precursor to Clean), DDD, Atomic design (fell out of fashion but fits components), and Feature-Slice design (enough structure to place logic, not too strict — great for front end). Trying to fit Clean architecture into a pure frontend feels clunky; don't follow one to a T. Maxi's approach: DDD subdomains → folder structure → boundaries = a modular monolith. Formal subdomain discovery: the "DDD Starter Modeling Process" repo.

03 · Stage 1 · Two halves

Modularity = organization + encapsulation

// organization: folders by subdomain
src/modules/{ catalog, orders, customers, authentication }
src/shared/            ui · api client · utils

// encapsulation: deps point DOWN; features never import siblings
// like private class members / ES-module exports — but for architecture
The missing half

Re-organizing folders is only half of modularity. The other half is encapsulation — familiar from OOP (private members), closures, and ES modules (only exports are public). Architecture has no built-in encapsulation, so we create the boundaries ourselves. Boundary types: module boundary (a module can't reach another module's internals), layer boundary (deps flow one way, down), and information hiding via an interface (expose an interface; others depend only on it). Other languages have ArchUnit; JS has ESLint rules.

03 · Stage 1 · Make it stick

A bad import fails CI

Enforced 3 ways: eslint-plugin-boundaries · Dependency Cruiser · Turborepo tags.

Boundaries as code

ESLint (works with Biome/OXLint too): no-restricted-imports built in; the boundaries plugin defines "elements" + dependency rules. Keep default:disallow so every new element forces a decision. Elements: shared + authentication = platform; modules/* capture the moduleName. Rule: a module may import platform + itself (captured name), never a sibling; allow type-only imports (checked at build). Errors dropped 106 → 31 → 18 → 2 as rules tightened; the final 2 were the real bug. Dependency Cruiser (npm run lint:deps) enforces the same, draws the graph, and can flag a "shared" file used by fewer than 2 modules (cohesion: things that change together belong together). These rules are also the guardrails AI agents hit on the next lint run.

04 · Stage 2

Split into packages

apps/ + packages/ · 3 steps: workspace → packages → tooling · a package's exports = its interface.

Folders become packages

Two ways in: decompose a monolith, or bring scattered repos together. Three-step adoption: (1) one workspace, (2) break into packages, (3) add tooling. Structure: an app shell (imports everything, the one deploy) + one app per module + packages ui, shared, tooling. Workspaces (npm/pnpm/Bun/Deno) let packages import each other without publishing to npm. A package's exports field is its interface — consumers get only the screens you expose. Still one build: only the app shell is deployed. (Branch: full-monorepo.)

04 · Stage 2 · Sharing code

Four ways to share

Shared packagesimple · can become a junk drawer
Interfaceexpose only what's needed
Duplicatefine for small logic
Dependency injectionslot pattern — decouples

If everything keeps moving to shared, rethink your abstractions.

Trade-offs

Options to share code across packages: move it to a shared package (easy, but becomes the junk drawer), expose a limited interface (what authentication does with its exports), duplicate (fine for small pieces), or dependency injection / the slot pattern (the app shell has a slot the builder fills — decouples the shell from the search feature). If you find yourself moving everything to shared, your abstractions are probably wrong.

04 · Stage 2 · Tooling

Turborepo

Caching + task orchestration + boundary tags · graph + devtools · catches cycles.

Speed + rules

Options: Turborepo, Nx (popular in JS), Bazel/Gradle (bigger scale/other langs), Lerna (legacy). They solve caching (local + remote) and task orchestration (build order). turbo.json: build dependsOn ^build (deps first), outputs ["dist/**"] so cache restores the folder; dev is persistent + no-cache. `turbo boundaries` checks cyclical deps, package-internal leaks, and undeclared deps (npm hoisting). Tags: per-package turbo.json tags ["platform"|"module"]; root denies platform → module. Tools: `turbo run build --graph` (mermaid), `turbo devtools`, generate, query.

05 · Stage 3

When micro-frontends?

An organizational problem — teams that must deploy independently.

Earn stage 3

Growing pains: teams need independent deploys (single pipeline = bottleneck), legacy areas you want to update one at a time, and diverging architectural drivers (different teams care about different things). Rule of thumb: adopt when the cost of coordinating the monolith exceeds the cost of running the distributed architecture. Both rise; adopt at the crossover.

05 · Stage 3 · Options

Flavors — start simple

iframeshard isolation · postMessage
Web Componentsruntime + isolation
Module Federationruntime code-sharing · default

Split vertical (by route) or horizontal (part of a view). Cheat: vertical-only → DIY proxy · isolation → iframes · Next.js → multi-zones · else → Module Federation.

The menu

Questions to pick a flavor: how to split (vertical = by route; horizontal = part of one view), where routing/rendering happen (server/client/edge), where to compose, and how much isolation. Flavors: iframes (isolation, postMessage), web components (runtime + isolation), native platform (edge-side includes, import maps), fragment-orchestration libs (single-spa — largely unmaintained; Piral, Qwik fragments), route-based (Cloudflare Workers, Next.js multi-zones), and Module Federation / Native Federation. Maxi builds it raw first (branch DIY): apps on separate ports, a proxy per route, an iframe for a horizontal piece, localStorage for same-origin state (use a secure cookie for auth). Cheat sheet: vertical only → DIY proxy (NGINX/Node/even Laravel); full isolation → iframes; Next.js → multi-zones; experiment → Qwik; otherwise Module Federation (safe, widely-supported, SSR).

05 · Stage 3

Module Federation

const A = lazy(() => import("analytics/Dashboard"));  // React = singleton
// <Suspense><ErrorBoundary> ... </></>  — a down remote can't crash the host
Core mechanism

Module Federation (from Webpack 5, now standalone — module-federation.io) is both a pattern and an implementation; plugins for Rsbuild, Rspack, webpack, Vite (Vite has no dev). It lets two independently-deployed apps share code at runtime. Host = app-shell; remote = analytics, exposing ./Dashboard via a generated remoteEntry.js. `shared` negotiates dependencies — React must be a singleton (same instance) or context breaks across the boundary. Import with React.lazy + Suspense + an error boundary; the classic bug is forgetting to await the import. `import:false` skips the fallback React when the host has it. Host and remotes can be different frameworks → great for incremental migration.

05 · Stage 3

Keep them independent

Component= reuse
Micro-frontend= independence

Few props · share state via Nanostores — expose a listener, not the atom.

MF 2.0: auto types + mf-manifest.json = service discovery (name → URL → version).

Independence is the point

Comms: iframes → postMessage; Module Federation → props/context (same React instance), events/message bus, or signals/atoms. Don't over-rely on props: a component is about reuse, a micro-frontend about independence — every prop couples them. Nanostores: the remote owns the state (atom) and exposes a listener, so consumers subscribe but can't mutate. Module Federation 2.0 auto-generates types (@mf-types → tsconfig) and adds mf-manifest.json — frontend service discovery. Version management schemas: AWS frontend-service-discovery, Vercel microfrontends.json. Turbo can do multi-version via separate builds (build V1/V2).

06 · The catch

Micro-frontends aren't free

CSS conflictsfix: Tailwind (atomic)
Duplicate depsversion skew
Many pipelinesharder to debug

Adopt from a cost analysis, never for novelty.

Honesty = senior signal

Downsides: CSS conflicts (which remote loads first) — fix with Tailwind, whose atomic utilities decouple styles the way atomic stores decouple state; duplicated deps + runtime version skew; and many pipelines to babysit. Adopt from a cost analysis. Showing trade-offs — not selling the shiny thing — is senior thinking.

06 · The payoff

Match the pattern to the pain

Pick by pain, not trend. Modularity before distribution.

The takeaway

The whole course in one table. Don't pick by trend — pick by pain. Always raise modularity before distributing. The smallest architecture that removes the pain wins. This is the slide to photograph.

07 · Modern angle

Architecture & AI

AI builds the structurescaffold · refactor · diagrams
You decide the boundaryAI can't

Boundaries = guardrails for agents; docs = context. Judgment is worth more.

Modern angle

Architecture fundamentals grow MORE important with AI, even as low-level tricks (refactoring) matter less. Context engineering: ADRs, specs and boundaries become the context you feed agents. Harness engineering: guidance so agents work autonomously. Boundary rules are the guardrails agents hit on the next lint/typecheck. Avoid full spec-driven development (a waterfall that ignores what you learn while building) — aim for "just-enough architecture," then iterate. AI builds the structure; deciding where the boundary goes stays human.
